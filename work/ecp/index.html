01背景

ECP（Enterprise Cloud Payment）是一套面向海外市场的支付平台，当前部署面向印度：币种为 INR，金额按印度数字分组显示。它对商户提供两类核心能力：

  • 代收（Pay-in）：消费者通过 UPI、Net Banking 付款给商户；
  • 代付（Pay-out）：平台按商户指令，通过 UPI、IMPS、NEFT、RTGS 打款到收款人账户。

围绕这两条资金链路，平台还要承担：

  • 商户：入驻与开通校验、API 凭证、IP 白名单、费率模板与规则、路由与返佣配置；
  • 账户：商户账户与平台账户（手续费收入、通道清算）、冻结 / 解冻、保证金计划、调账审批；
  • 交易：代收、代付、退款、充值、提现、批量代付，收款人白名单、风险名单、通知重试与人工处理；
  • 结算与对账：结算批次、审核打款、通道对账与差错单；
  • 争议：拒付（Chargeback）与网络投诉类争议的工作台。

商户直接用 API 接入，钱在平台账上进进出出，所以这套系统的底线很明确：每一分钱都要有来处、有去处，重复请求、重复回调都不能多记一笔。

03关键挑战

C1 · 结果不确定

回调会重复、乱序、迟到

代收的支付结果靠异步回调和查单确认，代付的结果可能长时间悬而未决。状态只能按合法方向前进，同一事实到达多次只能生效一次。

C2 · 商户直连

开放 API 要防伪造、防重放

商户系统直接调用下单与代付接口，请求必须可验证来源、不可被截获重放，网络重试也不能变成重复打款。

C3 · 账要对得上

多账户、多分录、冻结与保证金

一笔交易同时影响商户余额、平台手续费收入和通道清算账户；代付要先冻结，还有保证金、调账、退款和争议。

C4 · 本地化

印度市场的支付与合规细节

UPI / IMPS / NEFT / RTGS 不同的支付方式，PAN、GSTIN、IFSC、VPA 等 KYC 与收款字段，银行节假日与工作日，INR 的金额精度与显示。

04方案与架构

下图基于源码梳理，只展示高层设计，与首页「架构与实现」一致。

代收与代付：状态机 + 乐观锁 + 幂等

代收订单从“已创建”到“待支付”，再到成功、失败、超时关闭或异常；代付订单从“已创建”到“处理中”，再到成功、失败或异常。每次状态推进都带上版本号做乐观锁更新，并校验当前状态是否允许这次迁移，非法迁移直接拒绝。

通道回调、商户通知、定时任务、批量代付、结算重试和对账都按业务键 + 状态迁移守卫做幂等：同一事实重复到达，只返回已有结果，不再记账。进入异常态的订单走人工处理工作台，处理过程留痕。

开放 API：签名、防重放、幂等键

商户请求支持 HMAC-SHA256 与 RSA2 两种签名方式，校验时间戳与 nonce 防止重放，叠加 API 凭证、IP 白名单和幂等键；同一幂等键的重复请求不会重复创建订单。通道回调按原始报文验签，避免框架反序列化后再序列化造成的验签偏差。

账务：多腿复式记账与余额恒等

所有金额按最小货币单位以 Long 整数存储，不使用浮点数。每个账户维持 total = available + frozen 的恒等式；一笔交易会生成多腿分录，同时作用于商户账户、平台手续费收入账户和通道清算账户，借贷必须平衡。

代付发起时先冻结商户余额；成功时先解冻、再做多腿扣减并记入通道清算账户，失败则直接解冻。顺序上坚持先用乐观锁推进订单状态、成功后才动账，避免并发回调下重复解冻把冻结余额扣成负数。调账走审批流，保证金按规则冻结与释放；账务侧有定时的内部对账与账本完整性检查。

结算与对账：批次化、可重试、按银行工作日

当前代收结算以内部入账批次为单位：待审核 → 待入账 → 入账中 → 已完成；入账失败保留订单占用并允许重试，取消则按状态约束释放占用。订单到期日与结算时点按对应模式计算，涉及银行工作日的模式使用节假日日历。批次完成不等于渠道代付或银行到账；通道对账与差错处理是另外的业务流程。

风控、争议与数据安全

风险名单支持拦截与放行两类规则，代付收款人可走白名单；拒付与网络投诉类争议有独立工作台和订单事件时间线。敏感字段（证件号、银行账户等）落库加密、日志脱敏、不进入 toString，并有脚本做审计检查；平台支持多租户，定时任务按租户执行。

06交付情况

代收、代付、退款、充值、提现、批量代付，到结算批次、通道对账与差错单，整条资金链路在代码里完整实现。

钱的规则落在了代码约束里

整数金额、余额恒等式、多腿分录平衡、版本号乐观锁和幂等守卫统一收口在公共层，各业务模块共用同一套实现。

测试覆盖关键链路

两百余个测试类，覆盖签名与防重放、回调验签、幂等记录、多腿分录构建、账本完整性检查等关键路径（单元测试与集成测试）。

两套控台 + 开放 API
