01背景

信付通是信言科技面向三门峡本地商户的支付与行业数字化服务：以聚合收款为根基，联合成熟的行业软件伙伴，为餐饮、零售商超、民生缴费、教育校园、停车出行、酒店文旅等行业配齐点单、收银、会员、缴费系统；有特殊需求时，再围绕支付做定制开发。

资金由持牌支付机构直接结算给商户，平台不经手资金。但平台依然要对每一笔交易的状态、手续费、代理商分润和结算结果负责，而且要同时服务四类角色：

  • 商户：收款码、云音箱播报、对账与结算查询；
  • 代理商：多级代理关系、分润规则与分润后台；
  • 平台运营：商户进件审核、通道与路由配置、风控与账务处理；
  • 开发者 / 合作伙伴：通过开放 API 把支付能力接进自己的行业软件。

所以这不是做一个“能收钱的页面”，而是一套要长期跑下去、出了问题能说清楚每一分钱去向的支付平台。

架构与领域划分

03关键挑战

C1 · 结果不确定

外部调用会超时、断连、重复回调

调用支付机构时，“没收到响应”不等于“没扣款”。既不能重复扣款，也不能漏掉已经成功的交易。

C2 · 机构差异

每家机构的协议都不一样

请求号格式、签名方式、回调语义、查单与关单规则各不相同，还会随机构升级而变化，不能让这些差异渗进业务代码。

C3 · 账要对得上

手续费、分润、结算、退款都要记账

每一笔资金事实都要能追溯、可重放、不透支；出错时要能受控纠正，而不是直接改库。

C4 · 弹性与多端

早期要快上线，后期要能拆

起步阶段希望单体部署、运维简单；业务增长后能按域拆成微服务。同时要支撑多租户、多角色、多端和敏感数据保护。

04方案与架构

下图基于源码梳理，只展示高层设计，与首页「架构与实现」一致。

  • 01 · 先落库再调用

    调用支付机构前，先在本地事务里落库幂等键、订单、路由决策和状态恢复任务；结果未知时只查单、不重发。

  • 02 · 路由与适配

    在商户路由组内按优先级或最低预计成本选择通道；机构协议固化在版本化 Adapter 中，回调统一验签、归一。

  • 03 · 复式记账

    支付成功经 Outbox + RocketMQ 进入账务域，按业务身份幂等记账；分录只追加、余额不透支，每日做内部对账。

  • 04 · 月表与双拓扑

    高频交易、回调和流水按月分表；同一套源码既能单体运行，也能拆成 Gateway + 各业务域微服务。

支付链路：先落库，再调用；结果未知只查不重发

调用支付机构之前，先在一个本地事务里落库幂等键、支付订单、路由决策、本次执行尝试和状态恢复任务；只有真正创建了这些记录的请求，才在事务提交后发起外部调用，外部调用本身不放进数据库事务。

同一次尝试始终复用同一个机构请求号。一旦请求可能已经发出，超时、断连都按“待确认”处理：只能用原请求号查单或关单，不换号、不改路由、不新建替代交易。由数据库里的状态恢复任务承担“必须完成”的义务，消息队列只负责尽快唤醒，不作为事实来源。

通道路由与版本化适配

商户绑定路由组，在组内按优先级或最低预计成本选择通道。每家机构的协议细节——请求身份格式、签名、字段映射、回调解析——都收在版本化 Adapter 里；机构请求身份在首次外呼前固化，重试、查单、回调定位和对账都复用它。回调统一验签、归一成平台语义后，进入同一个状态收敛入口，用行锁加条件更新保证状态只按合法方向前进。

账务：Outbox + RocketMQ，复式记账，日终对账

支付成功在提交业务状态的同一本地事务里写入 Outbox，提交后经 RocketMQ 投递给账务域。账务按“业务身份 + 请求摘要”做全局幂等：同一事实重复到达返回原结果；同一身份却带着不同内容，判为冲突并告警，而不是悄悄覆盖。

记账采用复式分录，分录只追加、不修改；同一事务内按固定顺序加行锁，避免死锁；余额不允许透支。纠错走“原过账精确冲销”这类受控流程，形成新的、可审计的记录。每天以自然日的逻辑零点为截点做内部对账，任务晚跑几分钟也不影响结果。

跨域一致性：本地事务 + 显式契约，不上分布式事务

各业务域只在自己的本地事务里修改自己的数据。跨域协作按业务语义分级：必须先批准或锁定的用同步前置命令；来源事实已成立、目标随后必须处理的，用持久化投递 + 目标域幂等保证最终收敛；可以容忍少量丢失的非关键通知（比如播报）才用尽力而为的调用。网络超时一律视为“结果未知”，重试有退避、有超期告警、有人工处置入口。

数据与部署

高频交易、回调和流水按月分表，避免单表无限增长；多租户隔离，敏感字段按明文 / 加密 / 脱敏 / 哈希分级处理。同一套源码既能以单体运行（适合起步期），也能拆成 Gateway + 各业务域微服务，部署拓扑的变化不改变业务一致性规则。

06结果

官网已上线，可以直接打开

行业方案、定制开发、资金与安全、开发者等内容已对外：ciftopay.com。

一套源码，两种部署拓扑

同一代码库可单体运行，也可拆为 Gateway + 业务域微服务；起步期运维简单，扩展时不用重写。

资金链路的规则写成了“可执行的约定”

幂等、状态收敛、记账、对账、跨域一致性等关键规则以近百份架构决策记录沉淀，新成员和 AI 编程代理按同一套约束工作。

多角色、多端覆盖

运营 / 商户 / 代理三端 Web、uni-app x 移动四端、开放 API 与文档站，共用同一套后端能力。
