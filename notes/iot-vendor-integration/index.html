接入多家物联厂商：把设备协议留在集成层

史晓河2026-10-29约 5 分钟IoT · 架构
本文内容
  1. 统一的是业务动作，不是所有厂商的字段
  2. 启用检查要经过系统、功能和机构
  3. 本地实体与厂商实体必须能对上
  4. 把事件转换和业务处理分开
  5. Mock、自动化检查和真机联调各有边界

社区和校园都要处理人员、门禁、停车与安防，但设备厂商的接口、编号和事件格式各不相同。如果业务页面直接依赖这些差异，每换一家厂商，就要连着改人员管理、通行记录和考勤逻辑。润臻智慧大脑把厂商调用与事件归一放进独立的集成路径，让业务侧尽量围绕自己的模型工作。

关键判断
  • 对外调用按业务功能组织，厂商协议由对应实现承接。
  • 系统、功能和机构三个层级共同决定接口能否执行。
  • 先把事件转换成业务数据，再交给按事件类型选择的处理器。

统一的是业务动作，不是所有厂商的字段

“把一个人员同步到指定机构的门禁系统”是业务动作；某家厂商用什么字段表示人员编号、怎样签名、成功响应长什么样，是协议细节。集成层把请求准备、厂商执行、结果处理和同步记录组织在一条路径里。

这种统一有明确的边界。业务方不需要知道每家厂商的请求格式，但仍然要提供机构、实体类型、业务实体与功能。一个没有能力差异的万能接口，看起来简单，后面往往会长出更多隐含参数。

当前实现通过功能策略准备业务参数，再按功能与系统选择对应策略。共同流程负责映射和记录，具体客户端处理协议。这使新增适配可以落在相对集中的位置，但不代表新厂商永远只需加一个类。

启用检查要经过系统、功能和机构

一个厂商平台可用，不等于平台上的每个功能都已经开通，也不等于每个学校或社区都允许调用。项目在执行前分别检查系统、功能和机构配置的存在性与启用状态，任一层不满足就返回明确的业务错误。

层级要回答的问题
系统这个外部平台是否已登记并启用？
功能当前动作是否存在，是否允许使用？
机构这所学校或这个社区是否开通了对应接入？

这些检查集中在集成入口，可以减少控制器或业务服务各写一遍判断。权限与租户范围仍然需要由各自的边界保证，不能把“机构接入已启用”当成调用者已经获得授权。

本地实体与厂商实体必须能对上

本地人员 ID 与厂商人员 ID 是两套身份。接口成功之后，需要保存它们之间的映射，并记录同步状态；下一次更新或删除时，才能定位到真正的外部对象。

映射需要包含系统、机构、实体类型与本地实体等范围，不能只拿一个人员编号全局查找。对新增、查询、更新和删除等动作，当前流程会检查已有映射与状态，再交给具体策略处理。

这里最难的情况通常是外部已经执行、本地没有拿到明确结果。映射与日志能够提供调查线索，但不会自动解决所有重复创建问题。是否能按业务标识回查、是否支持幂等请求，需要逐个厂商确认；不能仅凭 HTTP 超时就认定远端没有创建。

把事件转换和业务处理分开

上行事件走另一条路径：先根据来源系统与转换类型选转换器，把厂商字段变成统一业务数据；再根据事件类型选处理器，执行通行、停车、考勤或其他业务操作。

转换器负责“这段数据是什么意思”，处理器负责“这件事在业务里要做什么”。这样，厂商变更事件字段时，通常先调整转换层；业务规则变化时，优先修改处理器，而不必把两者混在同一个大分支里。

处理器基类组织初始化、处理、完成与异常流程，并记录处理状态、次数和失败原因。当前工厂会在启动时检查映射并记录缺失告警；实际找不到对应处理器时返回错误。这些记录让失败可追踪，但单凭状态字段不能证明事件一定只生效一次，幂等仍需落在具体业务写入上。

Mock、自动化检查和真机联调各有边界

仓库提供 Mock 策略，可以在没有外部设备的情况下跑通部分调用组织与业务流程。它适合验证参数、配置选择、映射分支和错误处理，不能替代真实厂商的协议验证。

真正交付时，我会把检查拆开：先验证三级开关与实体映射，再用脱敏事件样本检查转换，随后联调设备返回、重复推送与异常恢复。摄像头和门禁的实际行为、厂商限流与网络条件，需要在对应环境里确认。

这种集成设计的价值，是把变化放到可以定位和测试的地方。它也有维护成本：策略命名要一致，映射要可追溯，缓存更新要有明确时机。抽象层如果只藏住错误、不保留失败原因，最后仍然得靠猜测排障。

本文依据项目当前集成与事件处理代码整理；本轮没有连接门禁、停车或安防设备，文中的联调项目是验证建议，不是新增的现场验收结论。
