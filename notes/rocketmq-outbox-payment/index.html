RocketMQ 与 Outbox：支付事实扇出、重试、死信，以及为什么后来改成有序直调

很多支付系统一上来就是“下单发消息、消费方各自处理”，好像 MQ 是支付架构的标配。信付通（CiftoPay）里 RocketMQ 的位置要克制得多：它只负责运输、缓冲和扇出，从来不是事实来源。这篇讲我们在“支付成功事实扇出”这个特性上做的一组决策——为什么不用 RocketMQ 事务消息、消息体怎么设计、重试和死信归谁、为什么不要顺序消息——以及后来为什么又把最关键的两条资金义务收回成了 Outbox 有序直调。最后这段演进我会如实讲，它比“一开始就设计对了”更有参考价值。

TL;DR
  • 事实先和业务状态在同一个本地事务里写进 Outbox，再由投递器发普通消息；不叠加事务消息这第二套可靠机制。
  • 消息是版本化的“最小完整事实”：固定信封 + 类型化载荷，不是只有 ID 的通知，也不是整张订单。
  • 每个领域事实一个 Topic、用 Tag 区分类型；每项义务一个消费组，各自负责 ACK、重试、死信和告警。
  • 不用顺序消息：重复和乱序靠业务幂等 + “依赖未就绪就重试”吸收。
  • 后来，记账和分润这两条有严格先后依赖的资金义务，改由 Outbox 按顺序直调；MQ 留给真正多订阅方的事实。

先问一句：这条链路为什么需要 MQ

引入 MQ 的理由只有一个：一个支付成功事实，要触发多个彼此独立的后续义务——账务入账、代理分润、收款语音播报，以及以后还会出现的报表、风控等。如果支付域逐个调用它们，支付域就得知道所有下游、跟踪每个下游的成败；下游越多，支付域越重。

但 MQ 带来的东西也很明确：至少一次投递、可能重复、可能乱序、Broker 本身可能不可用。所以第一条原则是：支付成功这件事是否成立，绝不取决于消息有没有发出去。事实在数据库里，MQ 只是把它搬给别人。

普通消息 + Outbox，而不是事务消息

RocketMQ 有事务消息：先发半消息，执行本地事务，再提交或回滚，Broker 收不到结论还会回查。看上去正好解决“业务和消息一致”的问题。我们最后选的是普通消息 + Outbox，理由有三：

  1. Broker 不可用时，支付成功也必须能落库。事务消息要求先把半消息发到 Broker，Broker 挂了，本地事务要么不做、要么脱离事务消息的保护。而 Outbox 是同一个本地事务里的一行数据，Broker 挂多久，它就安静地等多久，恢复后补发。
  2. 不为同一事实叠两套可靠机制。事务回查本质上就是“去查一下数据库里这件事成没成”——这正是 Outbox 投递器在做的事。两套机制同时存在，出问题时你得先判断是哪一套没兜住。
  3. 两种部署形态都成立。项目同时支持单体和微服务两种拓扑，Outbox 只依赖本地事务，两边行为一致；仓库里也有分别针对两种拓扑的冒烟脚本。

消息长什么样：版本化的最小完整事实

消息体有三种常见做法，我们都想过：

  • 只发 ID，消费方回查支付域：消息小，但每个消费者都回头调支付域，耦合和负载都回来了，支付域一抖，所有下游一起抖。
  • 发整张订单：消费方拿到一堆用不着的字段，任何订单表的改动都会变成消息契约的改动。
  • 发一个任意 Map：最灵活，也最没有契约。

最终的形态是固定信封 + 类型化载荷：信封里是事件 ID、事件类型、版本、租户、业务单号、发生时间；载荷是消费方完成义务所需的最小完整事实——金额、手续费、计价快照、代理价格快照等（为什么要带计价快照，见记账与分润那篇）。事件类型和载荷定义在支付域对外的 API 模块里，消费方直接依赖来源域的契约，不复制 DTO；也刻意不抽全仓通用的事件基类或泛型领域事件。

租户 ID 作为消息属性随消息传递，消费端统一的钩子会断言它非空并在租户上下文里执行消费逻辑。多租户系统里，“消费时忘了切租户”是一种很隐蔽的数据串号风险，放在框架层统一处理比靠每个 Listener 自觉可靠得多。

Topic、Tag 与消费组怎么划

  • 每个领域事实一个 Topic，Tag 表示事实类型。既不为每个消费者建一个 Topic（那等于生产方知道消费方），也不搞一个全局事件 Topic（所有人订阅所有东西，过滤全靠自觉）。
  • 每项义务一个消费组，集群消费而不是广播；消费组名按环境区分，避免测试环境的消费者抢走别的环境的消息。
  • 消息 Key 用业务单号，排查时能按单号在 Broker 侧直接检索。

发送端：只在 Broker 确认后标记已发

投递器按“到期 + 未被占用”领取 Outbox 行，领取时带租约和代次（generation）；只有拿到 Broker 的发送确认之后才把这一行标记为已发送，完成时也按代次条件更新，防止一个超时的旧实例把新实例的结果覆盖掉。

两条容易被忽略的约定：允许重复发送（标记失败后重发，消费方会看到两次，这是设计内的）；技术性发送失败永不因次数耗尽而放弃——达到告警阈值只告警，绝不把支付成功事实改成失败或删掉。固定间隔起初够用，只有积压真的证明它造成压力时，才改成有上限的退避。

还有一点是边界：Broker 确认之后，支付域的责任就结束了。支付域不跟踪“谁消费了没有”，不汇总下游状态，也不因为下游失败重新打开 Outbox。否则支付域又会变回那个什么都要管的中心。

消费端：先提交，后 ACK

消费方只在本模块业务事务成功提交，或者按稳定业务身份判定为幂等成功之后才 ACK。幂等靠的是业务唯一约束（例如“同一支付单号的入账过账只能有一条”），而不是消息 ID 去重表——事件 ID 在写 Outbox 时就固定了，但真正定义“同一件事”的是业务身份和事实摘要。

不预设 Inbox：只有某个模块确实需要把“接收”和“处理”拆开时，才为它单独加收件表或任务，不要求所有消费者套同一个流程。

重试、死信与 runbook

Broker 接收之后的失败恢复，归各消费组自己：技术异常、依赖未就绪交给 MQ 重投，重试耗尽进入该组的死信队列并告警。修复之后，所属模块按 runbook 使用 RocketMQ 自带的组级死信重投，保持原消息体、原 Key 和稳定业务身份。

runbook 里有两条“不做”：不直接改库来“修正”消费结果；不建设项目级通用重放服务。通用重放服务听起来很美，实际上它会变成一个能绕过所有业务校验、往任何消费者塞任何消息的后门。真需要人工重放时，只为明确的模块和场景加受控操作，并且人工不得修改消息体。

不要顺序消息：用幂等和“依赖未就绪”换

顺序消息在 RocketMQ 里要求同一分区键的消息进同一队列、单线程消费，一条卡住后面全堵。我们的选择是不用：重复和乱序由两样东西吸收——

  • 业务幂等：重复的事实撞业务唯一键，按摘要判定为幂等成功；
  • 依赖未就绪即重试：比如分润确认先于支付入账到达，账务发现平台账户余额还不足以覆盖分润，返回“依赖未就绪”，消息稍后重投，自然就排到入账之后了。

只有将来出现了真实的、无法用“依赖未就绪”表达的不变量，才考虑按支付单号做局部顺序。

版本演进：先部署消费者

版本规则很简单：只新增可选字段不升版本；删字段、改含义、改必填性才升版本。消费方显式校验自己支持的版本，收到不支持的版本不 ACK，最终进死信并告警——宁可停下来，也不要用错误的理解处理钱。发布顺序永远是先部署能识别新版本的消费者，再部署发新版本的生产者。每个 Listener 只用简单分支处理已知版本，不建版本注册中心。

后来的收敛：资金义务改回有序直调

上面这套是“支付成功事实扇出”特性的设计。后来在一次 Outbox 约定的统一整理中，我们把账务入账和代理分润这两条资金义务合并成一个订阅方，由 Outbox 投递器按顺序直接调用：先确认平台手续费账户已就绪，再入账，入账成功或幂等后再确认分润。原来为这两项义务准备的 MQ 订阅方因为没有引用被删除，并加了一个契约测试，双向比对 Outbox 的字典数据和代码里的枚举，防止“库里还有、代码里没了”这种漂移。收款播报和通道产品停用请求各自是独立的订阅方。

直调路径的可靠性完全来自 Outbox：领取带 60 秒租约和代次；下游返回分类结果，已过账/幂等算完成，事实冲突/业务拒绝算失败，依赖未就绪/技术可重试按 1、5、15、60 分钟退避；首次投递超过 24 小时仍未完成就转人工，人工重投必须带上期望的重试次数，防止两个人同时点；成功的 Outbox 保留 30 天后按每批 1000 条清理。

为什么改？下面是我回头看的判断，不是当时文档里的原话：

  • 这两条义务之间有硬依赖。分润必须在入账之后，退款时分润冲回必须在退款记账之前。在 MQ 上它们是两个独立消费组，只能靠“依赖未就绪→重投”间接排队，正确但会制造大量无意义的重试和告警噪音。
  • 两个消费者不值得一跳异步。MQ 的解耦价值在“多个、可增长、彼此无关”的订阅方；对两个强相关、同属资金核心的义务，它只多了一跳、多了一处要监控的积压。
  • 人工介入更清楚。一行 Outbox 就是一项资金义务的完整状态：做到哪一步、下游怎么回答、下一次什么时候试。比在两个消费组的死信里拼图要直观得多。

这不是否定 MQ。真正“一个事实、多个彼此无关的订阅方”的场景，前面那套 Topic/消费组/死信的约定依然是我们的标准做法。

如果重来

  • 先画依赖，再选传输。如果一开始就把“哪些义务之间有先后依赖”画清楚，记账和分润从第一天就会是有序直调，MQ 只承担播报这类彼此独立的订阅方，能省掉一轮实现和一轮删除。
  • 确定性拒绝不要只留在告警里。消费端对“事实冲突/业务拒绝”记告警后确认消费，理由是重试没有意义。但这样证据只存在于日志和告警系统里。我现在更倾向于把它们显式送进死信或落一张拒绝记录，让“需要人看的事实”有一个可查询、可重投的归宿。
  • 把 runbook 做成可执行的演练。“组级死信重投”写在文档里很清楚，但它应该在预发环境定期跑一次：制造失败、进死信、修复、重投、验证幂等。

小结

在支付链路里用好 RocketMQ，关键不在会用多少特性，而在守住边界：事实在数据库里，Outbox 和业务同事务；只在 Broker 确认后算发出，技术失败永不放弃；消息是版本化的最小完整事实；每个消费组自管 ACK、重试和死信；不用顺序消息，用幂等和依赖未就绪换；先部署消费者。再加一条后来学到的：有硬依赖的资金义务，有序直调往往比异步扇出更简单、更可靠。
