分润与记账模型：复式分录、逐级价差与按比例冲回

聚合支付平台的账务，难点从来不是“会不会复式记账”，而是：一笔钱在支付、分润、退款之间来回流动时，任何一次重试、并发、取整都不能让账多一分或少一分。这篇写信付通（CiftoPay）账务域和代理分润域的实际模型：账户怎么分、分录怎么写、分润怎么算、退款怎么冲回，以及每个设计背后防的是哪种错。代码是按真实模式改写的示意，金额一律是以“分”为单位的整数。

TL;DR
  • 账户按“用途”建模，每种用途有正常方向；余额分可用、冻结、待结算三态，分录逐条记录变动前后余额。
  • 所有过账走同一个写入器：至少两条、借贷相等且为正、币种一致、余额不得为负；账户按 ID 排序加锁。
  • 代理分润是自根向下的逐级价差，底价倒挂时按上级有效底价结算；平台预计利润不能为负。
  • 退款冲回按累计退费比例向下取整再减去已冲回部分，保证多次部分退款加起来恰好等于原分润。

一笔支付成功之后，账上发生了什么

支付域在订单成功的同一个事务里写下“支付成功事实”（见状态机那篇），之后由 Outbox 按顺序驱动两件事：账务入账，然后代理分润确认。退款反过来：先让分润域算出要冲回多少，再拿着分润的回执去做退款记账。

这条链路上有三类会让账出错的风险：重复（同一事实被投递两次）、并发（同一个平台账户被几十笔交易同时加减）、取整（按比例分摊时那 1 分钱去了哪里）。下面每一节基本对应其中一类。

账户模型：用途、方向、三种余额

账户不是按“谁”建的，而是按“谁 × 用途 × 币种”建的。用途包括通道清算应收、商户结算应付、平台手续费收入、代理分润应付、通道成本费用、退款手续费费用、追偿应收等。每种用途有一个正常方向：资产类借增贷减，负债和收入类贷增借减。记账代码不需要知道“这是资产还是负债”，只需要“这条分录的方向是否等于该用途的正常方向”。

每个账户的余额拆成三态：可用、冻结、待结算。支付刚成功、还没结算的钱记在待结算；提现申请会先把金额冻结，成功后再扣减，失败则解冻退回。分录上除了方向和金额，还标明它动的是哪一态。这让“商户能提多少钱”不需要临时计算，而是余额上直接可读的事实。

两张分录：支付入账与分润确认

两个刻意的设计：

  • 不写零金额分录。没有手续费的交易就没有手续费那一条；没有代理的商户，分润结果是“无代理”，根本不产生分润过账。零金额分录不改变任何余额，却会污染对账和报表，还会让“这笔有没有分润”变得含糊。
  • 分润确认依赖平台可用余额。如果平台手续费收入的可用余额还不够覆盖本次分润合计，账务返回“依赖未就绪”，而不是记出一个负余额。这正是 Outbox 要求“先入账，再确认分润”的原因之一。

写入器的硬规则

支付入账、分润确认、退款、提现、人工冻结解冻、人工冲销，所有场景最终都调用同一个账本写入器。场景只负责生成“过账计划”，写入器负责把关：

“每条分录自带前后余额”是对账时最有用的东西：任意一条分录都能和前一条首尾相接地校验，出现断点立刻就能定位到是哪一次过账。余额行上的“最后一次过账 ID”则是日终对账的截取水位（详见对账那篇）。

并发：排序加锁、复核与“读赢家”

平台手续费收入账户是天然热点：几乎每笔交易都要动它。并发策略有四点：

  1. 按账户 ID 排序后加行锁，余额和账户两组都按同一顺序锁。所有过账遵守同一个加锁顺序，就不会互相死锁。
  2. 锁内复核。锁之前做过的检查（过账是否已存在、账户是否就绪）在拿到锁后再做一次，锁外的判断只用来快速失败。
  3. 唯一键冲突时读赢家。两个实例同时为同一事实过账，后到的那个会撞上业务唯一键；这时不报错，而是读出先写成功的那条过账，按事实摘要判断是“幂等成功”还是“事实冲突”。
  4. 有限重试与跨日重算。技术性失败最多重试 3 次；如果重试期间记账日期变了（跨过零点），按新日期重新生成计划，因为分录要落到正确的业务月。

结果被归为六类：已过账、幂等成功、事实冲突、业务拒绝、依赖未就绪、技术可重试。上游 Outbox 只看这个分类决定下一步：前两类算完成，中间两类是终态失败要人看，最后两类按退避重试。分类比异常更好用，因为“重试会不会有用”这件事，只有账务自己知道。

事实摘要：怎么判断“同一笔”

幂等不能只看业务单号。同一个支付单号，如果第二次送来的金额、手续费或分润明细不一样，那不是重复，是矛盾。所以每次过账都会对规范化后的事实计算一个摘要，连同事实版本号一起存在过账头上。

长度前缀看起来多余，其实是在防一个经典歧义：如果只用分隔符拼接，"ab" + "c" 和 "a" + "bc" 可能得到同一串；字段值里本身出现分隔符时更糟。带上长度，拼接结果就和字段序列一一对应。版本号则保证事实结构升级后，新旧摘要不会被错误地拿来比较。

逐级价差分润与底价倒挂

代理体系是一棵树：每一级代理有自己的结算底价（按费率区间配置），商户付给平台的手续费减去直属代理的底价，就是直属代理的分润；上一级代理赚的是“下级底价 − 本级底价”。自根向下逐级算，这就是逐级价差。

现实中配置会出错：下级的底价可能被配得比上级还低（倒挂），或者比商户手续费还高。我的处理是计算有效底价：

没倒挂时，有效底价就是配置底价，结果等于相邻底价之差；倒挂时，下级至少按上级的有效底价结算，受影响的层级同时记录配置底价和有效底价，并打一条告警日志。这样分润永远不会出现负数，而配置错误也不会被悄悄“修正”掉——运营能看到哪一级、差多少。

算完各级之后还有一道总闸：平台预计利润 = 商户手续费 − 分润合计 − 预计通道成本，必须 ≥ 0，否则直接拒绝确认。分润结果分三种：无代理、零分润、正分润，只有正分润才会写分润确认的 Outbox、驱动账务记“分润确认”那张分录。

计价快照：让消费方能独立复核

手续费和底价都是按阶梯规则算出来的。支付成功事实里不只带结果，还带一份完整的计价快照：命中的规则区间、费率、固定费、最低最高费、命中下标、原始费用、套用最低后、封顶后、取整方式和精度、公式版本。

分润域和账务域拿到事实后，会只凭快照里的冻结参数重算一遍，任何输入、中间值、公式版本或结果不一致都拒绝。规则本身也有校验：区间必须从 0 开始且首尾相接，所有参数非负，封顶不得低于最低。

这是一种“不信任上游”的设计，代价是事实体积大了不少。我认为值得：手续费算错是最难事后发现的问题之一，而有了快照，任何一笔交易的手续费都可以在三年后被逐步复现，不依赖当时的规则配置还在不在。

退款冲回：按累计比例，而不是逐笔取整

部分退款时，代理分润要按退还的手续费比例冲回。最直觉的写法是每次退款算一次 分润 × 本次退费 / 手续费 再取整——这会系统性地丢钱。看一个例子：原分润 3 分，商户手续费 10 分，分三次退还手续费 3、3、4 分。

第几次本次退费逐笔向下取整累计退费累计应冲回 ⌊3×累计/10⌋本次冲回 = 累计 − 已冲回
13⌊0.9⌋ = 0300
23⌊0.9⌋ = 06⌊1.8⌋ = 11
34⌊1.2⌋ = 11032
合计101（少冲 2 分）3（恰好全额）

所以实际实现是：先按累计退费算出累计应冲回（向下取整），再减去之前已经冲回的部分。并且要求累计值单调不减——如果算出来比已冲回的还少，说明输入有问题，直接拒绝。全额退款时累计退费等于手续费，累计应冲回就精确等于原分润，一分不差。

退款记账的依赖顺序与责任账户

退款时顺序是固定的：先让分润域冲回，拿到冲回回执（每级冲回多少），再做退款记账。分润域没接受，账务就返回“依赖未就绪”或“事实冲突”，不会出现“钱退了、分润没冲”的中间态。

退款分录比支付复杂得多，因为退款发生时，原来那笔钱可能已经从待结算转成可用、甚至被提走了。做法是：

  • 对每个要扣减的原始分量，按余额态的优先顺序逐级扣减（例如先可用、再待结算），并扣除本计划里已经计划扣掉的部分，避免同一余额被重复计入；
  • 扣不够的缺口记到责任账户：代理分润的缺口记代理追偿应收，平台的缺口记平台费用，通道侧的缺口记通道应付；
  • 平台净退费 = 商户手续费退还 − 分润冲回合计；为负时说明分润冲回多于平台退出的手续费，差额贷记回平台。

每条退款分录还记着它冲回的是原过账里的哪一条分录序号，任何一分钱都能追溯到它最初是怎么进来的。

取舍与如果重来

选择得到付出
单一写入器 + 计划/执行分离所有场景共享同一套守卫，新增场景只写计划写入器成为高敏感代码，任何改动都要走全量账务回归
热点账户行锁实现简单，强一致平台收入账户是串行点；量大时要考虑汇总入账或子账户拆分
计价快照全量随事实传递任何一笔都能独立复核、多年后可复现事实体积大，版本演进要更谨慎
累计比例冲回多次部分退款不丢不多需要可靠记录“已冲回”的累计值，依赖分润确认记录加锁读取

如果重来，我会改两件事。第一，热点账户从一开始就预留拆分能力：现在平台手续费收入是单账户行锁，正确但串行；我会在模型上提前允许“同一用途多个子账户 + 日终汇总”，等量起来再改就要动历史数据。第二，把“过账计划”做成可以单独序列化和回放的对象：现在计划只在内存里存在，出问题时只能看结果分录反推；能把计划本身留档，排查和演练都会容易很多。

小结

账务模型的可靠性来自几条朴素的纪律：按用途建账户、按正常方向记分录；所有过账过同一道闸（平衡、为正、同币种、不为负）；固定加锁顺序、锁内复核、冲突读赢家；用规范化摘要定义“同一笔”；分润有效底价兜住配置错误，平台利润不为负；冲回按累计算。它们单独看都不复杂，但缺任何一条，都会在某个凌晨变成一张对不平的表。
