用 AI 编码代理交付支付系统：契约、门禁、验证与评审

信付通（CiftoPay）这个聚合支付平台，绝大部分代码是 AI 编码代理写的，主力是 Codex，Claude Code 也在用。我不觉得这值得炫耀——让 AI 写出代码很容易，让它写出我敢签字上线的支付代码，需要一整套放在仓库里的约束托底。这篇不谈提示词技巧，只讲这套约束本身：契约怎么写、需求和决策放在哪、门禁和验证怎么设计、评审看什么，以及几个真实踩过的坑。

TL;DR
  • 一份放在仓库里的 AGENTS.md 契约，两个代理共用；每条约定只有一个准源，目录规则补充根规则。
  • 最有价值的不是编码风格，而是业务不变量和工作边界：哪些事 AI 不能自己决定。
  • 需求、决策、票据、验收全是仓库里的 Markdown；提交门禁只做轻量、确定性的检查。
  • 动手之前先定“要证明什么”；交接时把本地测试、Sandbox、机构验收、生产验证分开说。

前提：AI 写的代码，最后都是我负责

支付系统的错误代价不对称：一个幂等漏洞可能在半年后的某个凌晨重复扣款。AI 代理的典型失败恰好集中在这里——它会写出能编译、能过测试、看起来很合理的代码，但在边界条件、并发和“不该做的事”上没有判断力。它不知道“通道超时不等于失败”，不知道“这张表不能直接改”，也不知道“共享的数据库不能随手清”。

所以我的分工很简单：我定义问题、不变量和验收标准，AI 在这个框里实现，然后由门禁、测试和评审证明它没越界。下面的所有东西，都是在把“框”写成机器和代理都能读的形式。

一份契约，两个代理

项目根目录的 AGENTS.md 是 Codex 和 Claude Code 共用的工作契约，进入子目录时要求代理主动读取最近的目录规则（后端、Web、移动端、SQL、脚本、文档各有一份），而不是依赖工具自动注入。几条核心原则：

  • 一条约定只有一个准源。跨域契约在根文件，单域细则在最近的目录规则，交付状态在票据里。变更时改指针，不复制整段规则——复制出来的规则一定会漂移。
  • 用户确认过的约定必须写进仓库，不能只留在某个工具的私有记忆里。换一个工具、换一台机器，它就没了。
  • 个人风格不进项目文件。项目文件只记录项目约束和入口，避免把一个人的偏好变成所有人的规则。
  • 通用方法和项目事实分开。研究、规格、拆票、TDD、评审这些通用方法用上游原版的技能包；项目只写一份“本地接口”文档，说明这些方法在本仓库里对应哪个目录、哪个字段。我曾经尝试按项目定制一份通用技能，后来整体撤销了——定制版和上游一旦分叉，就再也说不清哪个版本是对的。

把业务不变量写给 AI 看

契约里我最看重的一节是“业务不变量”。这些都是代码里很难自然表达、但违反一次就是事故的规则，例如：

  • 业务边界：哪些业务不在这个系统里（比如聚合支付不包含转账），相关域不得为它们加产品、接口或记账场景。
  • 敏感字段统一使用明文 / 密文 / 掩码 / 哈希四种后缀，前端和外部 API 不提交、不展示、也不感知哈希字段。
  • 平台业务编号一律走共享的编号入口（见对账与幂等）。
  • 跨域写和外部副作用只用本地事务，并在设计和验证里写明这次适用哪种一致性契约（见RocketMQ 与 Outbox）。
  • 设计开发阶段直接演进，不交付旧设计的兼容、降级或迁移层；分步重构可以短暂共存，但合入前必须切完调用方、删掉旧实现。
  • 金额、权限、状态流转、幂等和恢复路径的验证，不因为改动文件少而省略。

倒数第二条是专门针对 AI 的。代理天然倾向于保守：保留旧路径、加个开关、写个降级分支，看起来很稳妥，实际上会让系统里同时存在两套行为，而且旧的那套没人测。最后一条也是：AI（和人一样）会按改动大小估计风险，“只改了一行”就想跳过回归。在支付系统里，一行改的可能恰好是金额的取整方向。

领域语言单独放在一份一千多行的 CONTEXT.md 里：订单、支付尝试、通道回执、过账、有效底价……每个词的精确含义和不该混用的近义词。代理读了它，生成的类名、字段名和日志才会和业务讨论用的是同一套词。

需求、决策和票据都在仓库里

项目不用外部的需求管理工具，也不以 PR 作为需求入口，所有东西都是 docs/features/<特性>/ 下的 Markdown：

产物文件作用
原始需求或缺陷request.md尚未形成方案时可以单独存在，不为过门禁伪造规格
实施规格spec.md范围、设计、Testing Decisions
实施票issues/NN-slug.md一票一文件；Status、Blocked by、Branch、Owner 是独立的纯文本行
讨论与决策grill-notes.md、decisions/把“为什么这么选”和否决的方案写下来
验收票内“验收”一节门禁会检查；完成后在 Comments 记录验证命令、结果和限制

目前仓库里有 103 个特性目录、522 张实施票、96 篇架构决策记录、27 份决策讨论记录。数量本身不重要，重要的是两个性质：代理可以直接读到“为什么”，所以它不会推翻一个已经被否决过的方案；状态是可检查的纯文本，所以门禁能判断“这次提交声称完成的票，验收清单是不是真的写了”。

Grill-notes 是我最喜欢的形式：每条决策写成“问题 → 选择 → 理由 → 不做什么”。RocketMQ 那篇里“不用事务消息”“不用顺序消息”“不建通用重放服务”，都来自同一份记录。代理在后续实现时会遇到同样的诱惑，这份记录让它（和以后的我）不必重新讨论一遍。

门禁：只做轻量、确定性的检查

提交前门禁只有两项，都是秒级、确定性的：规则文档的指针和链接有没有断，本次实施的票据状态和验收清单格式对不对。编译、测试、业务旅程不放在提交钩子里，而是由 CI 按改动范围选择（后端、Web、移动端、官网、SQL 各自有范围判断，选择逻辑本身也有测试）。

原因很现实：慢的、偶尔失败的钩子一定会被绕过，无论是人还是代理。门禁的价值在于它永远会被执行。另一个细节是门禁只读暂存快照（本地）或 HEAD 范围（CI），不看工作区里没暂存的东西，避免“我本地是好的”这类结论。

门禁也有自己的测试。规则文档同步、票据状态、CI 范围选择各有一个自测脚本，覆盖坏指针、删除文件、暂存与工作区不一致、独立票、取消的依赖等场景。门禁错判比没有门禁更糟，因为大家会学会无视它。

验证：先定要证明什么

契约要求：动手之前先确定本次需要证明的行为和完整的验证集合，用规格时记在 Testing Decisions 里。开发循环里可以跑更小的检查，收口时必须完成定好的整套验证；只有新改动、失败或未解决的问题才扩大或重复检查。

这条规则解决的是 AI 代理的两个极端：要么改一点跑一遍全量，浪费几十分钟；要么只跑了刚写的那个测试就宣布完成。预先写下的验证集合是一个可以被检查的承诺。

测试分了几层：后端约 600 个测试类，其中 34 个是跨模块的契约测试（例如 Outbox 字典与代码枚举的双向一致性）；按业务旅程组织的端到端验证；以及单体和微服务两种部署拓扑各一份冒烟脚本，因为同一份代码在两种拓扑下的事务边界和调用路径不同。

修 bug 有一条硬规定：先复现失败，再修复，再用回归测试证明。AI 很擅长“修好”一个它没有真正复现的问题——改了某处，测试变绿了，但变绿的原因可能和 bug 无关。

交接的格式也是固定的：改动、执行过的命令和结果、未完成项、残余风险。并且本地测试、Sandbox、机构验收和生产验证必须分开表述。“测试通过”不等于“能收款”，这句话我在评审里说过很多遍，后来干脆写进了契约。

回归矩阵：不许写占位步骤

业务旅程有一张回归矩阵，每条旅程标注状态：可执行（有真实页面或公共 API，有依赖和自动检查证明业务闭环）、部分可执行（必须写明缺哪一环）、未具备条件（只有表或底层代码，不许写占位步骤）。

“不许写占位步骤”是这张表最重要的一句话。AI 非常乐意为一个还不存在的功能写出一份完整、漂亮的测试计划，读起来就像已经验证过一样。矩阵的备注列也遵循同样的诚实原则：大量条目写着“不代表真实机构”“不含生产验收”“只到某个环节为止”。一张诚实的“未完成”清单，比一份虚高的完成度报告有用得多。

评审：Standards 与 Spec 两轴

代码评审分两个轴独立看：Standards——是否符合项目规则和工程标准；Spec——是否实现了规格和票据要求的行为，有没有多做或少做。分开看是因为两类问题的发现方式不同：前者看代码，后者要对照需求逐条核对，混在一起很容易只做了前者。

评审的输入也有规定：固定点取当前分支相对主干的分叉点；先确认差异非空、方向正确；已提交的差异之外，还要提供暂存、未暂存和本次新增文件的全文。“空 diff 不代表工作区已审阅”——这是一个真实踩过的坑：代理对着一个空的已提交差异评审，得出“没有问题”。

踩过的坑

  • 辅助工具的存储失控。代码关系图谱是一个可选的导航工具（当前图里约 9.8 万个节点、32 万条边），它默认每次刷新都留一份日期备份，目录一度涨到约 11.8 GiB，清理后是 277 MiB。现在禁用了日期备份，图谱也明确不作为提交门禁，刷新放在后台、不适用时自动跳过。辅助工具不能变成交付的依赖。
  • 先实现、再合并、再删除。记账和分润最初各有一个 MQ 订阅方，后来合并成由 Outbox 投递器有序直调（见RocketMQ 那篇），旧订阅方因为没有任何引用被删除，并补了字典和枚举的双向契约测试。代理很少主动删除东西，“不交付兼容层”和“合入前删掉旧实现”这两条规则，正是让删除真的发生的原因。
  • 方法之间的冲突。不同来源的方法技能并非处处一致，例如“原型阶段不写测试”和“非平凡逻辑必须有可运行检查”会冲突。我的选择是不改上游、不加全局覆盖层，在具体任务里按当次请求和项目约束判断，并把这个已知冲突写在评审记录里。
  • 验证的“证明范围”被夸大。一次规则体系整理的验证记录里，我们特意写明：独立推演“验证的是规则路由，不是实际业务开发、共享数据库并发或模型长期稳定性的运行证明”。不写这句，读者（包括以后的代理）就会把它当成更强的证据。

取舍与如果重来

选择得到付出
仓库内 Markdown 管理需求和票据代理可直接读写，状态可被门禁检查没有看板视图；跨特性的全局进度要自己汇总
提交门禁只做轻量检查永远会被执行，不被绕过重检查都推给 CI，本地发现问题更晚
通用方法用上游原版不分叉、可升级和项目约束偶有冲突，需要按任务判断
不交付兼容层系统里只有一套行为每次重构都必须一次切完调用方

如果重来，我会更早做两件事。第一，从第一天就写业务不变量，而不是在评审里发现第三次同类问题之后才补。不变量越早写下，代理生成的代码越早“长”在正确的形状上。第二，更早引入业务旅程矩阵。单元测试证明的是零件，只有旅程能回答“商户能不能真的完成一次收款到入账”。

小结

用 AI 写支付系统，真正的工作量不在提示词，而在仓库里那些代理和人都必须遵守的东西：单一准源的契约、写清楚的业务不变量和工作边界、可被检查的需求与验收、轻量但永远执行的门禁、预先确定的验证集合、诚实的交接。它们不只约束 AI，也约束我自己——让“我觉得没问题”变成“这里是证据，这里是还没证明的部分”。
