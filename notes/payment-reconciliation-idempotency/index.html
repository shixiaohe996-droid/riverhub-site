聚合支付的幂等与对账：九层身份、编号、冲突判定与日终余额核对

“对账”和“幂等”在支付系统里几乎总被一起提起，但很多讨论停在口号：“接口要幂等”“每天对一次账”。这篇用信付通（CiftoPay）的实际实现讲得具体一点：幂等在每一层用的是什么身份、同号不同体怎么处理、日终余额核对的算法细节是什么、对出差异后怎么办，以及一个我必须如实说明的空白——通道对账单核对目前还没有做。状态机本身见上一篇，记账规则见记账与分润，这里不重复。

TL;DR
  • 幂等是一串分层的身份：从商户请求键、平台单号、通道请求号，到 Outbox 和过账的业务唯一键，每层防一种重复。
  • 每一层都同时做冲突检测：同一身份、内容不同，是矛盾而不是重复，必须拒绝并留痕。
  • 日终核对比较“锁内截取的余额倒推到截点”和“逐日累加的分录”，用过账 ID 做水位，三种余额态逐一比较。
  • 对账结果不可变，差异只能登记处理结论；修正一律走冲销过账，不改库。

幂等不是一个开关，是一串身份

一笔支付从商户请求进来，到最后变成账上的几条分录，中间会经过：商户重试、网关重放、通道超时后的查询或重放、回调重复推送、Outbox 重复投递、消费端重复消费、对账任务重复执行。任何一处只要多执行一次，就可能多扣一次款、多记一笔账、多发一次通知。

指望在入口加一个“幂等拦截器”解决所有问题是不现实的。每一层的重复来源不同，能用来识别“同一件事”的字段也不同。所以我的做法是：每一层显式定义自己的身份，并由数据库唯一约束做最终兜底。缓存和锁只是让常见情况更快，正确性永远落在唯一键上。

九层身份，各防一种重复

层身份防的是什么重复时冲突时
商户请求幂等键（24 小时）+ 请求摘要商户超时重试需凭查询令牌，常量时间比对后返回原结果摘要不同 → 幂等冲突
商户订单租户 + 商户应用 + 商户订单号换了幂等键的重复下单唯一键拒绝第二笔拒绝
平台单号前缀 + 业务日期 + 当日序列内部主键冲突唯一键兜底—
通道请求每次尝试固定的通道请求号超时后重放被当作新交易重放沿用同一号关单另起关单号
通道回执通道账户 + 操作 + 请求号同一请求被多个实例同时发出租约内只有一个实例发送同号不同体 → 冲突
回调原文摘要通道重复推送直接确认进入事实收敛判断
Outbox租户 + 类型 + 订阅方 + 单号状态推进重复写义务唯一键冲突即已存在—
过账场景 + 业务单号 + 事实摘要重复投递、重复消费读出已有过账 → 幂等成功摘要不同 → 事实冲突
对账结果账户 + 对账日对账任务并发或重跑保留先完成的结果—

表里最容易被忽略的是“重复时”那一列：幂等成功要返回和第一次一样的结果，而不是一个笼统的“已处理”。商户请求层要求重放必须携带第一次返回的查询令牌，服务端对令牌摘要和请求摘要都做常量时间比对，避免“猜到幂等键就能读别人的订单结果”。

平台单号：可解析、可恢复、最后靠唯一键

平台单号的格式是“业务前缀 + 业务日期 + 8 位当日序列”，序列来自 Redis 的原子自增，按“前缀 + 日期”分键。这个看似普通的格式承担了三件事：

  • 可解析：从单号就能解出业务日期，进而定位到按月分表的那张表，查询不需要额外的路由索引。
  • 有上限：单日序列达到 8 位上限时直接抛错，而不是悄悄溢出成 9 位，破坏下游的解析规则。
  • 可恢复：Redis 数据丢失时，序列会从头开始，可能和当天已发出的单号撞车。仓库里配了恢复脚本，从数据库里当天已发出的最大单号重新设定序列起点；而在恢复之前，数据库唯一键会让撞号的写入失败，不会产生两笔同号订单。

单号对外可见，按日递增的序列会泄露当天大致的交易量。对这个平台的场景，我接受这个代价，换来可读、可排查、可按月路由；对量级敏感的业务，可以在序列上做一层不可预测的映射。

同号不同体：幂等的另一半是冲突检测

只做去重的幂等是危险的。设想：账务消费端收到一条支付成功事实，业务单号已经有过账了，于是直接返回成功——但这次事实里的手续费和第一次不一样。如果它只认单号，就会把一个上游的严重错误静默吞掉。

所以每一层都是身份 + 内容摘要两段判断：身份相同、摘要相同，是重复，返回第一次的结果；身份相同、摘要不同，是矛盾，拒绝并告警。摘要要对规范化后的字段计算（固定字段顺序、金额用整数分、时间统一精度、字段带长度前缀），否则同一事实换个序列化方式就会被误判成冲突。过账层的具体做法在记账那篇里有代码。

还有一个细节：比较时空值不等于不同。比如早到的查单结果里没有通道流水号，晚到的回调里有，这不是冲突；但两边都有且不相等，就是冲突。把“缺失”和“不同”混为一谈，要么误报冲突，要么放过真正的矛盾。

对账到底在对什么

“对账”这个词至少包含两件很不一样的事：

  1. 内部一致性核对：账户余额是否等于它所有分录的累加。它能发现记账程序 bug、绕过写入器直接改余额、分录丢失这类问题。
  2. 外部核对：平台记录的交易和通道对账单是否一致。它能发现“通道成功了、我们没收到回调也没查到”的长款，或者“我们记了成功、通道没有”的短款。

信付通目前实现的是第一种，按日、按账户自动执行。第二种是下一阶段的工作，第 9 节单独说。

日终余额核对：截点、水位与回退

难点在于：对账任务跑的时候，交易还在继续。你不能为了对账停掉记账，但“现在的余额”已经包含了截点之后的交易。做法如下：

几个关键点：

  • 用过账 ID 做水位，而不是时间。同一账户的所有过账都在该账户行锁内写入并更新“最后过账 ID”，所以对单个账户来说，ID ≤ 水位精确等于“截取时已经提交、已经计入余额”。只用时间做边界，会在毫秒级并发和时钟精度上出错。
  • 流水侧逐日累加。每天只扫当天分录，成本和日交易量成正比，而不是和账户历史成正比。代价是流水侧会继承前一天的结果，但账面侧每天独立取数，一旦有差异会持续可见，不会被掩盖。
  • 三种余额态分别比较。总额对得上而态不对（比如该在待结算的钱跑到了可用），同样是要拦住的问题——它直接影响商户能提现多少。
  • 只对过去的日子。对账日必须早于今天；截点之后才创建的账户不参与。
  • 算术溢出直接失败，未知的余额态直接失败，不做“尽力而为”的跳过。

结果不可变，差异只登记结论

每个账户每天一条对账结果，同时记录截取时的水位、账面三态和流水三态。它有几条约束：

  • 已有结果就跳过，任务可以随便重跑；并发跑时由唯一键保留先完成的那条，后来者直接放弃。
  • 结果不可修改。出现差异时，运营只能对“未处理”的差异登记处理人和处理结论，登记动作写操作日志；已经处理过的不能再改。
  • 查询限制在连续三个自然月内，因为分录按月分表，跨太多月的查询会变成全表扫描。

“为什么不允许重新对账覆盖结果”是我被问得最多的问题。答案是：对账结果本身就是审计证据。如果差异修好后可以重跑覆盖成“平”，那么“曾经出现过差异”这件事就消失了。正确的流程是：差异保留，登记结论，修正走冲销，第二天的结果自然恢复为平。

错了怎么办：冲销，而不是改库

账务里没有“改一下数据”。任何修正都是一笔新的过账：人工冲销必须关联原过账，生成与原分录方向相反、金额完全一致的分录，同样经过写入器的全部守卫（平衡、为正、不为负、加锁顺序）。冻结、解冻也是过账场景。这样，任何时刻的余额都可以由分录完整重放出来，日终核对也才有意义——如果允许直接改余额，核对能发现差异，却永远说不清差异从哪来。

还没做的：通道对账单

必须坦白：通道对账单核对在当前代码里还没有实现。我把它当作下一阶段最重要的事，设计上已经为它留好了位置：

  • 匹配键现成。每次尝试固定的通道请求号和回执里冻结的通道流水号，就是逐笔匹配的键；状态机已经保证了它们不会被覆盖。
  • 差异分三类：通道有、平台无（长款），平台有、通道无（短款），双方都有但金额或状态不符。长款要走“查询 → 收敛”的同一条路径补齐，而不是绕过状态机直接改成功。
  • 修正复用冲销。对账单发现的问题，最终落到账上依然是关联原过账的冲销分录，以及差错处理记录。

在它上线之前，外部一致性靠的是：每次尝试都有恢复任务，不会有处理中的订单被遗忘；以及冲突事实会告警并停用对应的通道产品。这能挡住大部分问题，但挡不住“通道成功、我们永远没收到任何信号”的情况——这正是对账单核对存在的意义。

取舍与如果重来

选择得到付出
每层独立身份 + 唯一键兜底每种重复都有明确防线，易于测试身份多，新人要先理解整张表
幂等同时做冲突检测上游错误不会被静默吞掉需要稳定的规范化摘要，字段演进要带版本
日终逐日累加流水侧成本与日量成正比依赖前一天结果，首次或断档时要从头累加
结果不可变对账结果可作为审计证据差异修好后历史上仍保留差异记录，需要运营理解

如果重来，我会把通道对账单核对排在日终余额核对之前，或者至少同时做：内部一致性是程序正确性的问题，外部一致性是资金安全的问题，后者的优先级应该更高。另外，我会让流水侧每月做一次“从账户创建起全量累加”的校验，用来发现逐日链条里早期就存在的问题。

一份检查清单

  • 每一层的幂等身份是否写清楚了，并且有数据库唯一约束兜底？
  • 幂等命中时，是否返回与第一次相同的结果？重放是否需要凭证？
  • 同一身份、内容不同时，是否拒绝并告警？“缺失”和“不同”是否区分？
  • 单号序列丢失后，有没有恢复手段？恢复前是否不会出现重复单号？
  • 对账是否用水位而不是时间截取？是否按余额态分别比较？
  • 对账结果是否不可修改？修正是否只能通过冲销过账？
  • 是否有外部对账单核对？没有的话，哪些异常目前是兜不住的？

本文基于我在信付通（CiftoPay）项目中的实际设计整理，代码为脱敏后的示意改写。
