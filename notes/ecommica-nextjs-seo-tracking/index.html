Ecommica：Next.js 多语言 SEO 与点击归因的工程细节

Ecommica 是我从零做的一个优惠信息聚合站：前台是 Next.js（App Router + next-intl，英文和中文两种语言），后台和管理端是 Java。这类站点的收入来自联盟佣金，所以它的生死只取决于两件事：页面能不能被正确地搜到，以及用户点出去之后，那次点击能不能和最终的转化对上。这篇写这两条链路的实际实现、我在回看代码时发现的坑，以及要怎么改。站点域名、合作的联盟和商家都不在本文范围内。

TL;DR
  • 跳转路径 /go 由 Nginx 直接转给后端，不经过 Next：少一跳，也不受中间件和缓存影响。
  • canonical 和 hreflang 必须每页自己声明；写在根 layout 里，没覆盖的子页面会把 canonical 继承成首页。
  • Sitemap 要警惕静默截断（分页上限）和“全部是现在”的 lastModified。
  • clickId 在服务端生成并随跳转带给联盟；Postback 按 clickId 直接归因，找不到的进未归因队列。
  • “永远返回 200”能防止联盟重试风暴，但处理异常时会丢转化——应该先落原始回调，再处理。

背景：一个靠“被搜到”和“记得住点击”活着的站

站点内容是商家、优惠活动、优惠码、分类和博客。流量绝大部分来自搜索引擎和投放；用户点“去购买”，经过我们的跳转链接到达商家或联盟的落地页；成交后，联盟通过服务器回调（Postback）告诉我们“某次点击产生了一笔佣金”。

路由：哪些路径不该进 Next

多语言用 next-intl 的中间件实现，默认语言是英文。中间件的匹配规则排除了 api、go、Next 的内部路径和所有带扩展名的静态文件。这里有两个刻意的决定：

  • 无语言前缀的路径重定向到默认语言，而不是返回 404。代码注释写得很清楚：否则像 /categories 这样的 URL 会落到带 noindex 的 404 页，而 hreflang 的 x-default 恰好指向无前缀 URL——等于告诉搜索引擎“默认版本”是一个不可索引的页面。
  • 跳转路径不进 Next。/go/… 在 Nginx 层直接转给后端。跳转是纯粹的“记录 + 302”，没有任何渲染需求；绕过 Next 意味着少一跳延迟，不会被中间件加上语言前缀，不受 ISR 缓存影响，Next 进程重启时跳转也照常工作。对一个按点击计费的站来说，跳转的可用性比页面更重要。

canonical 与 hreflang：别放在根 layout

每个有内容的页面都在 generateMetadata 里声明自己的 canonical（带语言前缀的自身 URL）和 en/zh 两个语言版本。问题出在根 layout：它也声明了一份 alternates，canonical 指向站点根。

Next.js 的 metadata 是逐字段合并的：子页面没写 alternates，就会继承 layout 的那份。回看代码时我发现，关于、FAQ、联系、隐私政策这些页面只写了标题、描述和 OG，没写 alternates——于是它们的 canonical 全都指向首页。对搜索引擎来说，这等于说“这些页面是首页的重复”，它们可能永远不会被单独收录。这些页面本身流量不大，但同样的错误一旦出现在内容页上，就是灾难。

另一个不一致：layout 里英文版本指向无前缀的根 URL，而各页面里英文版本指向 /en/…。两个都“能用”，但同一个站里必须只有一种说法。修法是把它收敛成一个函数，所有页面只调用它，根 layout 不再声明 canonical：

Sitemap：静默截断与假的 lastModified

Sitemap 用 ISR，每 10 分钟重新生成一次：静态页面列表，加上从后端拉取的商家、优惠、博客和分类。每个条目都带 en/zh 的 alternates。这里有三个坑，都是“不报错、但结果是错的”：

  • 静默截断。商家、优惠、文章各拉一页，每页 200 条。内容超过 200 条之后，多出来的部分就不在 sitemap 里了，而且没有任何报错。正确做法是分页拉全，或者超过阈值时拆成 sitemap index。
  • 降级会被缓存。拉取失败时只返回静态页面，这在构建时是合理的兜底（构建环境可能连不上后端）。但运行时如果后端短暂不可用，这份“只有静态页”的 sitemap 会被缓存 10 分钟，正好被爬虫抓到。至少要在降级时打告警，并考虑在运行时失败时返回 5xx，让爬虫下次再来，而不是给它一份残缺的答案。
  • lastModified 全是“现在”。除了博客使用发布时间，其他条目的修改时间都是生成时刻。搜索引擎很快会学会忽略一个永远在变的信号。应该用实体真实的更新时间。

渲染策略：ISR 的时间窗

商家详情和优惠详情页用 ISR，5 分钟重新验证；博客详情改成动态渲染，缓存放在 API 请求层。选择 5 分钟的理由很直接：优惠信息需要比较新，但不需要实时；每次请求都打后端，在爬虫高峰时代价太高。

ISR 带来一个业务层面的取舍：一个优惠码在后台下架后，最多还会在前台展示 5 分钟。对优惠站来说这是可以接受的，但前提是跳转链路本身是实时的——用户点下去时，后端看到的是最新的目标，而不是页面缓存里的旧链接。这也是跳转必须走后端的另一个原因。

地区识别：可信代理与“安全但无声”

同一个页面在不同国家展示不同的优惠。地区的优先级是：URL 参数 > Cookie（30 天）> IP 定位 > 全球。IP 定位用本地的国家级 GeoIP 库，不依赖外部服务。

难点在“哪个 IP 才是用户的”。请求经过 CDN 和 Nginx，用户 IP 在请求头里，而请求头是任何人都能伪造的。前端的实现是保守的：

两个要点：X-Forwarded-For 要从右往左解析，因为最左边的值是客户端自己写的，最右边才是离你最近、你最能信任的那一跳；只有连接对端确实是可信代理时，才相信代理头。

这种保守实现有一个容易被忽略的失效模式：如果调用方拿不到或者忘了传连接对端地址，它会把所有代理头都拒绝，IP 定位静默地全部回退到“全球”。不会出错，不会有安全问题，页面照常渲染——只是地区化悄悄失效了。所以“识别失败”必须有计数指标，回退比例异常时告警。安全的默认值不等于不需要监控。

点击记录里的 IP 和国家用于反作弊和报表，所以后端取 IP 时也应遵循同样的规则。前后端最好共用同一份可信代理列表和解析规则，而不是各写一套。

点击：服务端生成 clickId

用户点“去购买”时访问的是 /go/{类型}/{ID}，类型是商家、Offer、优惠或优惠码之一，可以带最多五个 sub 参数。后端的处理：

  1. 按类型和 ID 找到目标实体，拿到目标链接和所属租户；目标不存在就报错，类型非法就回首页。
  2. 在目标所属的租户上下文里，由服务端生成 clickId（26 位随机串），连同目标、商家、国家、UA、Referer 和 sub 参数写入点击记录。
  3. 构造最终链接：目标链接里有占位符就替换，没有就把 clickId 作为 subid 参数追加；然后 302。

为什么 clickId 一定要服务端生成：客户端生成的 ID 可以被伪造、被重放；广告拦截插件会屏蔽前端埋点；而服务端跳转不依赖 JavaScript，任何能跟随 302 的客户端都会被记录。clickId 由我们生成、由联盟原样带回，归因就不需要任何 Cookie 匹配或设备指纹。

无论走占位符还是追加参数，sub 参数都来自用户可控的 URL，拼进跳转链接前必须做 URL 编码（示意里的 enc()）。否则一个带 & 或 # 的值就能篡改目标链接的参数结构，轻则归因错乱，重则把用户带到不该去的地方。

JS 200 跳转页

投放场景还有一条路径：部分投放平台要求落地链接返回 200，而不是 302。为此后端有一个 JS 跳转页：记录一条投放点击（媒体侧点击 ID + sub 参数），返回一个极简 HTML，用 location.replace 跳到目标，并带一个 <noscript> 的 meta refresh 兜底。

这类页面是 XSS 的高发区，因为它把一个部分由用户控制的 URL 同时放进了 HTML 属性和 JavaScript 字符串里。原则只有一条：按上下文转义——放进属性要做 HTML 属性转义，放进脚本要做 JS 字符串转义，而且要额外转义 <，因为 JSON 序列化本身并不能阻止值里出现 </script>。最稳妥的做法是把 URL 放进 data- 属性，由一段固定的脚本读取，脚本本身永远不拼接任何变量。任何把数据序列化进 <script> 标签的地方都适用同一条规则。

Postback：去重、未归因队列与“永远 200”

联盟在转化发生后调用我们的 Postback 接口，带上 clickId、联盟侧的转化 ID、类型、佣金和币种。处理流程：

  1. 按联盟编码查找配置。未知联盟：写入未归因队列，原因“联盟不存在”。
  2. 校验签名。签名应该是硬门槛：校验不通过就不该继续处理，至多记一条可审计的拒绝记录。
  3. 按“联盟 + 联盟转化 ID”去重，重复回调直接忽略；数据库上的唯一索引是最终兜底，防住并发的两次回调。
  4. 按 clickId 查点击。clickId 缺失或查不到：写入未归因队列，原因分别是“缺少 clickId”和“点击不存在”，并保存原始请求，留给人工处理。
  5. 找到点击，创建一条“待审核”的转化，佣金和币种按回调原样保存。

归因模型就是“clickId 直接归因”：一笔转化属于且只属于回调里那个 clickId，天然是最后点击归因。没有 Cookie 窗口、没有模糊匹配。代价是联盟没把 clickId 带回来时，我们就归不了因——所以未归因队列不是边角功能，而是这个模型的必要组成部分。

接口无论处理结果如何都返回 200，注释写明是为了防止联盟重试。这能避免一个 bug 引发的重试风暴，但也有代价：处理过程在一个数据库事务里，如果中途抛出异常，事务回滚，转化记录和未归因记录都不会留下，而联盟收到了 200，也不会再重试。这笔转化就只剩一行错误日志了。

这和支付回调是同一个模式：先把外部事实安全落地，再处理。返回 200 的含义应该是“我已经收到并保存了”，而不是“我试过了”。

取舍

选择得到付出
/go 绕过 Next，Nginx 直达后端跳转延迟低、可用性独立于前台路由规则分散在 Nginx 和中间件两处，需要一起维护
ISR 5 分钟爬虫高峰下后端压力可控下架内容最多滞后 5 分钟展示
服务端 clickId + 直接归因不依赖 Cookie 和前端埋点，归因确定联盟不回传 clickId 时无法归因，需人工处理未归因队列
保守的可信代理判断不会被伪造的请求头欺骗配置不全时静默失效，必须有监控
Postback 永远 200避免重试风暴异常时丢转化（应改为先落原始回调）

如果重来

  • SEO 元数据从第一天就只有一个出口。一个 alternatesFor()，加一个构建后的 canonical/hreflang 校验脚本。这比任何 SEO 插件都有用。
  • Postback 先做收件箱。原始回调先落库，签名、去重、归因在后台按状态推进；失败可以重放，而不是只剩日志。
  • 前后端共用一套客户端 IP 规则，并为“识别失败率”和“未归因率”建指标。这两个数字是这个站最重要的健康信号，比 PV 重要得多。
  • 所有跳转相关的拼接都写成带测试的工具函数：URL 编码、HTML 属性转义、脚本内转义各一个，每个都有包含 &、#、"、</script> 的测试用例。

小结

做一个联盟优惠站，技术难度不在页面，而在两条“看不见的链路”：搜索引擎看到的元数据和点击到转化的身份传递。前者要求每页的 canonical 和 hreflang 一致、sitemap 完整而诚实；后者要求跳转独立可用、clickId 服务端生成、拼接处处编码、外部回调先落地再处理。这两条链路出错时都不会报错，所以它们最需要的不是更多功能，而是校验脚本和监控指标。
